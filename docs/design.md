## 0. 목적

이 문서는 PRD의 F-03(카테고리별 Accent Color), F-04(슬라이드 타입 카탈로그 기반 고정 템플릿), F-05(D-Day 계산 제거) 요구사항을 실제 제작 규칙으로 구체화한다. AI가 매번 새로 디자인하지 않고, 여기 정의된 **고정 슬라이드 타입에 데이터만 매핑**하는 것이 원칙이다. 콘텐츠 생성 단계(Claude API)는 이 문서에 없는 색상·레이아웃·폰트 크기를 임의로 만들지 않는다.

v2는 "정제된 리포트" 톤은 유지하되, 다음을 함께 달성하도록 설계됐다: **(1) 첫 장에서 3초 안에 스크롤을 멈추게 하는 후킹, (2) 한 장 = 한 메시지로 가독성 극대화, (3) 저장하고 싶은 정보(체크리스트/HOW-TO), (4) 공유하고 싶은 한 장, (5) 마지막 장의 명확한 행동 유도(CTA).**

---

## 1. 브랜드 톤

* **정체성:** "저장하고 싶고 공유하고 싶은, 그런데 AI가 대충 만든 티는 안 나는" 정제된 카드뉴스. 리포트의 신뢰감 + SNS 콘텐츠의 후킹력을 함께 가져간다.
* **금지 사항:**
  * AI 생성 티가 나는 화려한 그라디언트, 3D 아이콘, 과도한 일러스트, 반짝이 이펙트 금지.
  * 토스(Toss) 스타일 카피/컬러/일러스트 오해 소지가 있는 디자인 금지.
  * "D-7", "D-DAY" 등 계산된 날짜 표기 금지 — 마감일은 항상 `YYYY.MM.DD(요일)` 절대값으로만 표기.
  * 한 슬라이드에 두 가지 이상의 주제/메시지를 넣지 않는다.
* **레이아웃 원칙:** 그리드 기반 정렬, 넉넉한 여백, 텍스트 위계는 크기보다 **굵기·색상 대비**로 표현. **한 슬라이드에 결론(또는 정보) 1개, 문장은 최소화하고 핵심 단어 중심으로 크고 명확하게 표시한다.**

## 2. 캔버스 규격

* **비율:** 4:5 (Instagram 피드 최대 노출 비율)
* **크기:** `1080 × 1350px`, 72dpi 이상 렌더링 (실제 렌더링은 2x = `2160 × 2700px` 스크린샷 후 다운스케일 권장, 텍스트 선명도 확보)
* **세이프존:** 상하좌우 각 `72px` 안쪽에만 핵심 텍스트 배치 (인스타그램 UI 아이콘/캡션에 가려지는 하단 `160px`는 특히 주의)
* **슬라이드 수:** 템플릿 타입별로 고정 (5장 참조) — 리포트형(대외활동/자격증) 6장, 브리핑형(뉴스) 8장, 간결형(인턴/채용) 6장.
* **산출물:** 슬라이드마다 데이터가 채워진 **HTML 파일을 우선 산출물로 보존**하고, 이미지(PNG) 변환은 그 다음 별도 단계로 수행한다 (수정 용이성 확보 — 8장 참조).

### 3.2 카테고리별 Accent Color (F-03)

| 카테고리 | Accent 토큰 | HEX | 사용처 |
| :--- | :--- | :--- | :--- |
| 뉴스/트렌드 | `--accent-news` | `#0FAE7A` (Emerald Green) | 배지, 포인트 라인, 강조 숫자 |
| 대외활동 | `--accent-activity` | `#06B6D4` (Cyan) | 배지, 포인트 라인, 강조 숫자 |
| 자격증 | `--accent-license` | `#F59E0B` (Amber) | 배지, 포인트 라인, 강조 숫자 |
| 인턴/채용 | `--accent-job` | `#1E5EFF` (Electric Blue) | 배지, 포인트 라인, 강조 숫자 |

> 정해진 발행 시간표는 없다 — 카테고리는 운영자가 그때그때 직접 고르며, Accent Color는
> 시간이 아니라 카테고리에만 매여 있다 (하나의 포스트에 두 색을 섞지 않음).

Accent 컬러는 다음 요소에만 적용한다: 상단 카테고리 배지, 좌측 포인트 바(4px), 강조 숫자/마감일, target 체크마크, hero_fact/ai_analysis의 핵심 수치. **일반 본문 텍스트에는 accent 컬러를 쓰지 않는다** (`--ink-900` 고정) — 가독성과 "정제된" 톤 유지. 표지(cover)만 예외적으로 사진 배경 위에 흰색 텍스트를 사용한다 (4장 참조).

| highlight 값 / 라벨 | 38px / 22px | ExtraBold(800) / SemiBold(600) | 항목 1~2개, hero_fact보다 작지만 target보다 큼(v2.6) |
| 캡션/출처/워터마크 | 20px | Regular(400) | 모든 슬라이드 공통 하단 |

**문장 길이 상한 (7장 접근성 체크리스트와 연동):** 표지 헤드라인 22자 이내, hero_fact 보조문구 20자 이내, target/caution/highlight/ai_analysis의 pros·cons 항목 40자 이내(ai_analysis의 score_label, ai_response의 reason은 20자 이내), 그 외 본문 슬라이드 50자 이내. 이 상한을 넘기면 문장을 자르지 말고 **문장 자체를 더 짧게 다시 쓴다.**

## 5. 슬라이드 구성 (템플릿 타입)

고정 6슬롯 방식(v1)을 폐기하고, **슬라이드 타입을 순서대로 나열하는 유연한 리스트**로 바꾼다. v2.6부터는 카테고리 3그룹(리포트형/브리핑형/간결형)이 서로 다른 시퀀스와 "분석" 슬라이드를 쓴다 — 다 같은 틀에 욱여넣으면 내용 전달력이 떨어진다는 피드백 때문이다. 타입별 HTML 템플릿과 변수 스키마는 고정되어 있으므로("AI가 매번 디자인하지 않는다", F-04), Claude는 오직 어떤 타입을 쓸지 고르고 그 타입의 필드를 채우는 것만 한다.

### 5.1 슬라이드 타입 카탈로그

각 타입은 `templates/_slide_macros.html` 안에 같은 이름의 Jinja2 매크로(예: `cover(...)`, `hero_fact(...)`)로 구현되어 있고, `templates/_deck.html`이 카드의 `slides` 리스트를 순회하며 각 항목의 `type`에 맞는 매크로를 호출해 카드 1세트를 하나의 HTML로 조립한다 (타입별 개별 HTML 파일로 나뉘어 있지 않음).

| type | 매크로 | 역할 (한 슬라이드 = 한 메시지) | 쓰이는 곳 |
| :--- | :--- | :--- | :--- |
| `cover` | `cover(...)` | **후킹.** Gemini로 생성한 배경 사진(블러 완화) + 화면 하단 40% 이내를 차지하는 큰 후킹 헤드라인 | 모든 템플릿, 항상 1장, 맨 앞 |
| `hero_fact` | `hero_fact(...)` | 가장 중요한 사실(마감일/핵심 수치)을 초대형 텍스트로 제시하고, `extra_items`(2~3개)를 보조 정보 목록으로 함께 붙인다 | 모든 템플릿, 항상 1장 |
| `info_grid` | `info_grid(...)` | 사실을 label/value 행으로 나열. 리포트형/간결형에서는 `hero_fact.extra_items`로 흡수되어 예외적으로만 쓰지만, **브리핑형(뉴스)에서는 두 번 사용**(v2.7): 대표 뉴스 상세 1장 + 나머지 뉴스 브리핑 1장 | 브리핑형 항상 2장 / 그 외 예외 |
| `target` | `target(...)` | 추천 타깃("이런 사람에게 추천") — 브리핑형에서는 라벨을 "왜 중요한가"로 바꿔 재사용 | 모든 템플릿, 항상 1장 |
| `ai_analysis` | `ai_analysis(...)` | **스펙로그 AI 시성비 평가 (리포트형 전용).** 이 소재를 **준비하는 데 드는 노력 대비 얻는 경쟁력**을 점수(0~100)+근거 한 줄로 매기고, Pros/Cons 2단 비교를 붙인다 | 리포트형(대외활동/자격증) 항상 1장 |
| `ai_response` | `ai_response(...)` | **스펙로그 AI 추천 대응 (브리핑형 전용).** 점수가 아니라 "그래서 지금 뭘 해야 하는가"를 한 문장으로 제시하고 근거를 붙인다 — 뉴스는 지원 여부를 판단하는 게 아니라 트렌드에 어떻게 대응할지가 중요하기 때문 | 브리핑형(뉴스) 항상 1장 |
| `highlight` | `highlight(...)` | **스펙로그 AI가 찾은 특별한 점 (간결형 전용).** 점수·Pros/Cons 없이 이 공고를 다른 공고와 차별화하는 사실 1~2개(정규직 전환율, 실무 프로젝트 등)를 label/value로 강조 | 간결형(인턴/채용) 항상 1장 |
| `caution` | `caution(...)` | 지원 시 맹점/주의사항 (최대 2개, warn 배경) — 예: "학기 중 제한". 실제 산출물에서 유용하다는 피드백에 따라 **세 템플릿 모두 항상 포함**(v2.6) | 모든 템플릿, 항상 1장 |
| `outro` | `outro(...)` | **명확한 CTA** + 출처 | 모든 템플릿, 항상 1장, 맨 뒤 |

> v2.7: 어느 템플릿에서도 쓰이지 않던 `tip`/`checklist`/`shareable`은 카탈로그에서 완전히
> 제거했다(매크로/CSS/스키마 항목 삭제). "나중에 쓸 수도 있으니 남겨둔다"는 이전 원칙을
> 폐기하고, 실제로 쓰이는 타입만 유지한다 — 다시 필요해지면 그때 다시 만든다.

### 5.2 카테고리별 템플릿 & 권장 시퀀스

**타입 A — 리포트형 (대외활동/자격증), 총 6장 고정:**

```
cover → hero_fact(마감일 + 기관/대상/혜택) → target(추천 타깃: 전공/원하는 직무 등)
→ ai_analysis(준비 노력 대비 경쟁력 점수 + Pros/Cons) → caution(지원 시 맹점) → outro
```

**타입 B — 브리핑형 (뉴스/트렌드), 총 8장 고정 (v2.7: 정보량 강화):**

```
cover → hero_fact(대표 뉴스 핵심 수치/한줄 사실)
→ info_grid(대표 뉴스 상세: 무슨 일이 있었나, 사실 3~4개)
→ info_grid(이번 주 더 챙길 소식: 나머지 뉴스 2~3건 전부 브리핑)
→ target(라벨을 "왜 중요한가"로 치환) → ai_response(스펙로그 AI 추천 대응: 지금 뭘 해야 하는가)
→ caution(해석 시 주의점) → outro
```

"1분 1초가 아까운" 취준생에게 뉴스 1건만 깊게 파는 대신, `research_gemini.py`가 수집한
뉴스 4건을 전부 활용해 그날의 취업 동향을 빠짐없이 브리핑한다 — 대표 1건은 hero_fact +
1번째 info_grid로 깊게, 나머지는 2번째 info_grid로 간결하게.

**타입 C — 간결형 (인턴/채용), 총 6장 고정:**

```
cover → hero_fact(마감일 + extra_items: 기관/회사명 + 지원 방법 + 전형 일정)
→ target(지원 자격: 원문의 구체적 조건) → highlight(스펙로그 AI가 찾은 특별한 점)
→ caution(지원 시 맹점) → outro(source_text에 지원 링크)
```

채용 정보는 "어디에, 어떻게, 누가 지원하는지"가 카드만 봐도 분명해야 한다(v2.9) —
hero_fact.extra_items에 기관(회사명)·지원 방법을 반드시 채우고, target은 막연한 인물상이
아니라 원문에 있는 구체적 자격 요건(학년/전공/어학/경력 등)을 items로 보여준다. outro의
source_text에는 원문의 지원 링크를 그대로 담아 지원 경로를 남긴다.

세 템플릿 모두 `cover`·`hero_fact`·`target`·`caution`·`outro`는 항상 포함하고, 템플릿을 구분 짓는 "분석" 슬라이드(`ai_analysis`/`ai_response`/`highlight`)와 뉴스만의 `info_grid` 2장이 실제 차이를 만든다.

**분석 슬라이드 작성 원칙 (뻔한 콘텐츠 방지, 공통):**
* **브랜딩(v2.7):** `ai_analysis`/`ai_response`/`highlight`의 heading에는 항상 "스펙로그 AI"를 붙인다 — "AI 분석"처럼 브랜드 없이 쓰지 않는다. 이 세 슬라이드가 스펙로그만의 차별점이라는 걸 문구로도 드러낸다.
* `ai_analysis.score`(0~100)는 "정보 자체의 가치"가 아니라 **이 소재를 준비하는 데 드는 시간/노력 대비 실제로 얻는 경쟁력**을 근거로 매긴다 — 손 가는 대로 비슷한 점수를 반복하지 않는다. `score_label`(20자 이내)에 근거를 한 줄로 남긴다.
* `ai_analysis.pros`/`cons`는 공고 원문을 그대로 옮기지 않는다 — "왜 유리한지" / "왜 불리하거나 번거로운지"를 각 1~2개, 항목당 20자 이내로 압축한다.
* `ai_response.response`는 팔로우/저장 같은 CTA가 아니라 **이 트렌드에 대한 구체적인 대응 행동**이어야 한다("포트폴리오에 이 키워드부터 추가" 등). `reason`에 왜 지금 그래야 하는지 한 줄을 붙인다.
* `highlight.items`는 "지원하세요" 류의 뻔한 말이 아니라 이 공고를 검색 결과의 다른 공고와 구분 짓는 **사실**이어야 한다(전환율, 처우, 실무 범위 등 숫자·고유명사 위주).
* 표/차트 같은 장식적 시각 자료는 추가하지 않는다(1장 브랜드 톤 "AI 티 나는 화려한 그래픽 금지"와 상충) — `ai_analysis`의 점수 바 + Pros/Cons, 그 정도의 절제된 표현이면 충분하다.

## 6. 표지(cover) 배경 이미지 가이드

* **생성 방식:** Gemini 이미지 생성 모델(`gemini-2.5-flash-image`, `pipeline/generate_cover_image.py`)로 소재 주제에 어울리는 사진풍 배경을 생성한다.
* **프롬프트 원칙 (v2.4: 더 현실적이고 소재에 구체적으로):**
  * 사람 얼굴/텍스트/로고가 들어간 이미지는 피한다 (초상권·저작권 이슈, 그리고 텍스트가 이중으로 겹치는 문제 방지).
  * "photo-realistic, editorial photography" 톤을 명시하고 "3D render, illustration, cartoon, AI-art style"은 명시적으로 배제한다 — AI 티 방지.
  * 카테고리 무드는 일반적인 배경이 아니라 **그날 소재(topic_hint)를 반영한 구체적인 장면**으로 구성한다: 뉴스/트렌드=해당 이슈와 관련된 산업/오피스 현장, 대외활동=관련 활동을 하는 학생들의 실루엣/뒷모습, 자격증=해당 시험 준비를 연상시키는 책상/자료, 인턴/채용=해당 기업·직무를 연상시키는 사무 공간 — "아무 사진"이 아니라 "이 얘기구나" 싶은 사진이어야 한다.
* **처리 (v2.4: 블러 완화):** CSS `filter: blur(10px)` + `scale(1.05)`(블러 시 가장자리 여백 방지) + `--cover-overlay-top`→`--cover-overlay-bottom` 세로 그라디언트를 얹어 상단은 은은하게, 하단(텍스트 영역)은 진하게 어둡힌다. 이전(v2.0~v2.3)의 `blur(28px)`는 사진이 무슨 내용인지 알아보기 어려울 정도로 과했다는 피드백을 반영해, 배경이 무엇인지 알아볼 수 있는 수준으로 낮췄다 — 텍스트 가독성은 오버레이 그라디언트가 담당한다.
* **텍스트 배치:** 후킹 헤드라인은 캔버스 하단 40% 영역 안에서 좌측 정렬, 흰색(`#FFFFFF`), ExtraBold. 카테고리 배지는 상단 고정.
* **폴백:** Gemini 이미지 생성이 실패하거나 키가 없으면, 사진 대신 해당 카테고리 accent 컬러의 짙은 그라디언트 배경으로 대체한다 (`templates/cover.html`에 내장된 CSS 그라디언트 폴백, 별도 이미지 파일 불필요).

## 7. 접근성 · 안정성 체크리스트

* 텍스트 대 배경 명도 대비 4.5:1 이상. 표지는 오버레이 그라디언트로 대비를 확보한다 (6장).
* 문장 길이 상한은 4장 표 하단 규칙을 따른다.
* 모든 슬라이드 우하단에 `@speclog.official` 워터마크 20px 고정 삽입 (캡처 유통 시 출처 표기). 표지에서는 흰색, 그 외에는 `--ink-300`.
* 한 슬라이드 = 한 메시지 원칙 위반(두 개 이상 주제 포함) 여부를 콘텐츠 생성 후 검수한다.

## 8. 데이터 매핑 & 파일 규칙 (F-04)

* 콘텐츠 생성 단계(Claude API)는 `pipeline/schema.py`의 `slides: [...]` 리스트 구조로만 출력하고, 렌더러는 각 항목의 `type`에 맞는 템플릿에 나머지 필드를 그대로 주입한다 ("디자인"이 아니라 "채움"만 발생).
* 마감일 등 날짜 필드는 항상 `"2026.09.15(화)"` 형식의 문자열로 고정하고, 파이프라인 어디에서도 D-day 계산 로직을 두지 않는다 (F-05).
* **생성 1회 = 폴더 1개로 정리한다 (v2.8):** `output/{yyyymmdd}_{생성시각HHMM}_{category}/` 폴더 하나에 그 생성의 산출물을 전부 모은다. `slot`은 더 이상 예약된 발행 시간이 아니라 파이프라인을 실제로 돌린 시각(HHMM)이다 — 정해진 업로드 시간이 없으므로, 나중에 찾기 쉽도록 언제 만들었는지만 남긴다.
* **HTML을 1차 산출물로 보존하되, 카드 1세트 = 파일 1개로 묶는다 (v2.1):** 폴더 안 `deck.html` 하나에 표지부터 아웃트로까지 전체 슬라이드가 순서대로 담긴다 (`templates/_deck.html`). 문구를 다듬고 싶을 때 PNG를 다시 생성하지 않고 이 파일 하나만 열어 스크롤하면서 확인/수정할 수 있다.
* PNG는 여전히 슬라이드별로 나온다: 같은 폴더 안에 `{순번2자리}.png`. 통합 HTML을 한 번만 로드한 뒤 각 슬라이드(`.canvas` 요소)를 개별로 스크린샷해서 만든다 (렌더러가 알아서 처리, 수동 작업 없음).
* 카테고리 코드: `news`, `activity`, `license`, `job`.
